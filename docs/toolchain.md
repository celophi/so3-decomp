# Building and matching functions

The build currently reproduces the complete US boot executable and all 15
recovered EE overlays. Most functions are still assembly placeholders, with
original data kept in binary pieces. The first two source matches are list-sentinel
comparisons in Field and Lib. Five small C probes also match their
original function bytes. I'm using that compiler candidate for now, but I haven't
identified the exact original compiler and flags for every module yet.

## Running the build

Build the development image and extract Disc 1 first, as described in the
[README](../README.md#docker-environment). From the repository root:

```sh
make split
make build
make verify
```

`make split` creates missing C/C++ sources and generates assembly, binary pieces,
macros, and linker scripts. Existing source files are preserved. `make build`
also runs Splat when needed, so you don't have to split manually before every
build. It checks or fetches the compiler, compiles and links, then compares the
complete output against the original.

Boot is written to `build/boot/SLUS_204.88`, with its comparison report in
`build/boot/verify.json`. Each overlay has its own rebuild and report under
`build/overlays/<id>/`. `make verify` repeats the comparison on those existing
files without rebuilding them.

## SDK code

Confirmed SDK functions stay as `INCLUDE_ASM` in `src/sdk/<module>/`. They are
excluded from objdiff and decomp.dev progress, but remain in the linked binaries
and whole-file verification. [config/sdk-functions.json](../config/sdk-functions.json)
records the reviewed ranges, hashes, and identification evidence.

The first pass identifies 151 EE kernel syscall wrappers in boot. Other library
and compiler runtime code remains unclassified. The optional analysis commands
are listed in the [README](../README.md#tools).

## Initial drafts with m2c

I'm using [m2c](https://github.com/matt-kempster/m2c) for the first pass at a
function. Its PS2 target supports CodeWarrior and C++. The revision and download
hash are pinned in `config/analysis-tools.json`; the downloaded tool stays local
under `tools/m2c/`.

```sh
make m2c
make decompile MODULE=1070-00 FUNCTION=func_00288650
```

Run `make split` first if the assembly hasn't been generated. Use `MODULE=boot`
for the resident executable, or the overlay ID for an overlay. The command
checks the original binary and the selected function's assembly bytes before
running m2c. It chooses `mipsee-mwcc-c` or `mipsee-mwcc-c++` from the configured
source extension. `LANGUAGE=c++` overrides that choice for an experiment.

Each run goes in `working/matching/<function>/<module>/m2c/run-NNN/`, with the
input assembly, draft, diagnostics, hashes, and command. Repeating it creates a
new run. Existing candidates and project sources aren't overwritten.

To supply known types and declarations:

```sh
make decompile MODULE=1070-00 FUNCTION=func_00288650 CONTEXT=working/context.h
```

The context must contain preprocessed C declarations, even for a C++ target.
m2c copies it into the run directory. A draft can still contain guessed types,
unknown fields, or unsupported instructions. C++ mode doesn't recover the
original class hierarchy. I still need to check the callers, recover the
interface, and compare the compiled function before moving a draft into `src/`.

## Replacing a placeholder

[src/boot/func_00101510.c](../src/boot/func_00101510.c) is a small example of
the edit, compile, and compare loop. Its placeholder can be replaced by this
zeroing loop, which already matches in the compiler probes:

```c
#include "include_asm.h"

void *func_00101510(unsigned int *object) {
    int i;
    for (i = 0; i < 16; i++) {
        object[i + 16] = 0;
    }
    return object;
}
```

Then run `make build` and `make verify`. This checks the complete boot file,
including the code around the function. A mismatch reports the first differing
file offset. Keep the function's symbol name and its position in the source
file while replacing it; both affect how it fits into the existing layout.

The scaffold still keeps this function as a placeholder. The example above
has been checked in the full build. Source, headers, and configuration are
tracked in Git. Assembly under `build/` is regenerated by Splat, so changes
made only there won't last.

## C++ support

Field (`1070-00`) and Battle (`3253-00`) use 54 `.cpp` units. I found 101 distinct
printable strings containing `.cpp` in Field and 319 in Battle. For example,
Field references `AtrCharacter.cpp` at file offset `0x151880`, and Battle
references `BattleApp.cpp` at `0x1FCAC8`. There's direct evidence of C++ use in
those overlays, even though the original classes and source boundaries still
need to be worked out.

Other game units keep the `.c` extension from the initial scaffold. **That
choice is provisional.** I haven't established that all of those functions
were originally C. Units can move to C++ as the code and interfaces become
clearer. The boot executable also contains `std::bad_alloc`, though runtime
library code could account for it.

The configured subsegment type determines the source language:

| Splat subsegment | Source | Compiler language |
| --- | --- | --- |
| `c` | `name.c` | `-lang c` |
| `cpp` | `name.cpp` | `-lang c++` |
| `asm` | Generated `name.s` | PS2 assembler |

[tools/so3/build/compile.py](../tools/so3/build/compile.py) selects the language by extension and
rejects other extensions. The explicit flag matters: mwccgap's second compiler
pass uses a temporary `.c` file even when the original source is C++. Both
passes need the same language setting.

Splat's `create_c_files: true` option creates `.cpp` files for `cpp` subsegments
too. To change an existing unit, rename its source and change its YAML
subsegment type together, then run `make build`. Remove the old source filename
as part of the rename. The linker script is generated from the configuration.

Existing assembly uses address-based names such as `func_00101510`. Give a C++
replacement C linkage if it keeps one of those symbols. For the zeroing-loop
example, put this declaration before the function definition in the `.cpp` file:

```cpp
extern "C" void *func_00101510(unsigned int *object);
```

The definition inherits that linkage. Shared headers can use `#ifdef __cplusplus`
around an `extern "C" { ... }` block. Classes and methods use normal C++ linkage;
as those interfaces are recovered, their compiler symbol names need to agree
with Splat symbols and assembly references. Don't put class declarations inside
the C linkage block. mwccgap already handles C linkage for its placeholder stubs.

The build uses the pinned compiler's historical C++ dialect and its default ABI
settings. RTTI, exception handling, and the other ABI choices still need matching
evidence from original C++ functions. A successful class test shows the build
can compile and link C++; it doesn't identify SO3's original settings.

Original data is still retained, and BSS hasn't been reconstructed. Vtables,
RTTI, static initialization, exception tables, and runtime calls will need
verified section mapping and interfaces for functions that use them.

## Compiler findings

The current working configuration is **CodeWarrior PS2 3.0 build 52, July 22
2003, with `-O3,p -RTTI off -inline level=4`**. I haven't uniquely identified it
as the original compiler. The two later flags come from Field evidence: the
vtables have no RTTI pointers, and some destructors inline four levels of base
destructors, which the default depth of three doesn't reach (see
[field-cpp-build.md](field-cpp-build.md)). Adding `-inline level=4` changed no
existing match in any module.

The comparison on 2026-09-29 covered 15 archived PS2 compiler candidates from
September 2000 through May 2004. Their versions, archive hashes, and individual
executable/DLL hashes are in [config/compilers.json](../config/compilers.json).
The archives come from the
[decomp.me compiler release](https://github.com/decompme/compilers/releases/tag/compilers)
and are downloaded under ignored `build/compilers/` when needed. The working
`mwccps2.exe` has this SHA-256:

```text
4a9d1289d2b444e240d79dd7f579eb2c0179f15d191fe51c0ac7d387e6de646c
```

Three builds matched all five probes, each at two optimization settings:

| Compiler candidate | Matching flags |
| --- | --- |
| 3.0 build 38, March 7 2003 | `-O3,p`, `-O4,p` |
| 3.0 build 50, May 27 2003 | `-O3,p`, `-O4,p` |
| 3.0 build 52, July 22 2003 | `-O3,p`, `-O4,p` |

| Original virtual address | Compared bytes | Probe behavior |
| --- | ---: | --- |
| `0x00101250` | 16 | Pointer arithmetic with a large field offset |
| `0x00101510` | 64 | Zeroing loop unrolled eight stores at a time |
| `0x0010A080` | 40 | Conditional update and reload through a potentially aliasing pointer |
| `0x0010A0B0` | 48 | Two conditional stores and a pointer reload |
| `0x0011EE00` | 104 | Queue insertion, wraparound, and repeated index loads |

That's 272 compared bytes, including delay slots and internal NOPs. The names
and C types were reconstructed. The queue probe uses a volatile index to get
the observed loads; matching the bytes doesn't establish the exact declaration
or source spelling used by the original developers.

To run the working candidate's checks:

```sh
make compiler-probe
```

This compiles [tools/so3/build/probes/boot.c](../tools/so3/build/probes/boot.c), compares full function
lengths and bytes, and writes `build/compiler-probes/report.json`. The probes
need no SDK headers or libraries and have no code relocations. The checker
rejects unresolved relocations rather than skipping their bytes. It also uses
symbol section indices because Metrowerks objects can have several sections
named `.text`.

For the full matrix:

```sh
make compiler-matrix
```

That fetches all 15 candidates and tries optimization levels 0 through 4 with
both speed (`p`) and size (`s`) preferences. The results go into
`build/compiler-probes/matrix.json`. Calls, floating-point operations, global
data, and C++ behavior are useful next probes for separating the candidates
that currently tie.

The boot ELF's `.comment` contains `MW MIPS C Compiler (2.4.1.01)`, but that
string isn't enough to choose a compiler. Local objects from several older
releases contain it: 2.4, 3.0 from November 2001, 3.0.1 from January 2002, and
3.0.3 from July 2002. The three builds that match the probes emit a `3.0.0`
comment instead. An older linker or an input library might explain the final
ELF's comment. I don't know its source yet.

The working archive also contains a linker reporting 3.0 build 27, May 7 2003.
Its banner runs under wibo, but the build uses PS2 binutils for linking. I
haven't established which linker SO3 used. SDK/library routines and IOP code
also need their own compiler investigation; the five probes cover resident EE
code only.

## Development container

repository root. `make image` runs the equivalent of:

```sh

```

The tools are pinned so a change on the host doesn't change the output while
I'm trying to match a function. The image currently uses:

## Assembly baseline

Both discs' boot executables contain the same 750,512 bytes and have this
SHA-256:

```text
7b58c4b0b1997711ba5c224ed8699e306671ff0ca3558afed17cff81b86fe8ed
```

The ELF has an empty symbol table and one nonempty, unnamed loadable section.
The first load maps file offset `0x680` to `0x00100000`, with file size `0xB6400`
and memory size `0xDD380`. Its entry point is `0x00100008`. Startup instructions
and `.reginfo` agree on global pointer `0x001BDFF0`.

[config/boot.us.yaml](../config/boot.us.yaml) uses these initial boundaries:

| File range, end exclusive | Bytes | Handling |
| --- | ---: | --- |
| `0x000000–0x000680` | 1,664 | Keep the original ELF header and program headers |
| `0x000680–0x044200` | 277,376 | Disassemble and reassemble resident EE code |
| `0x044200–0x0B6A80` | 469,120 | Keep resident data and unresolved VU/data contents |
| `0x0B6A80–0x0B73B0` | 2,352 | Keep original ELF metadata and section headers |

Startup stays in assembly. The five probe functions and unclassified resident
code have C placeholders under `src/boot/`; identified syscall wrappers are under
`src/sdk/boot/`. Explicit function boundaries are recorded in
[config/symbols.boot.txt](../config/symbols.boot.txt).
The last observed EE routine returns at `0x00143B24`, followed by its delay-slot
instruction at `0x00143B28` and padding up to `0x00143B80`. Data follows that
boundary. This layout comes from inspection; I don't have an original link map.

Splat uses `create_c_files: true` with automatic empty-function decompilation
disabled. Even empty functions start as placeholders. The same approach covers
the 15 overlays and their separate initializer regions. Splat retains 19 raw
`.word` entries in the boot assembly region; code, data, and VU boundaries still
need more work.

[tools/so3/build/driver.py](../tools/so3/build/driver.py) generates a Ninja graph at `build/build.ninja`.
It compiles source, assembles placeholders, turns retained binary pieces into
objects, links intermediate ELFs, and uses objcopy to write the original layouts.
The resulting files match without patching any differing bytes after linking.
Keeping the ELF wrapper allows a full-file check while the historical
linker's header-generation behavior remains unresolved.

The five C probes are checked separately and aren't yet linked into the committed
scaffold as source. The [overlay notes](overlays.md) cover the other 15 rebuilt
files. IOP rebuilds, disc packaging, and emulator testing remain future work.

## Assembly processor and dependencies

CodeWarrior needs an assembly processor for the `INCLUDE_ASM` workflow.
[mwccgap](https://github.com/mkst/mwccgap) reserves space for each placeholder,
assembles its `.s` file with PS2 binutils, then imports the bytes, symbols, and
relocations into the compiled object. Actual C and C++ definitions are compiled
normally. `include/include_asm.h` rejects compilation outside the project wrapper, since
otherwise those empty placeholder macros could silently drop functions.

The image pins mwccgap commit `147598b36b198f267e80adbe04dd5804d070dbb3` and checks
its archive hash. Its MIT notice is kept in
[dockerfiles/mwccgap.LICENSE](../dockerfiles/mwccgap.LICENSE) and at
`/opt/mwccgap/LICENSE` in the image.
[dockerfiles/mwccgap.patch](../dockerfiles/mwccgap.patch) fixes imports of local
symbol relocations. Local symbols are scoped to their assembly object, section
indices are remapped, and relocation indices are resolved after symbols have
been inserted. The upstream path assumed rodata existed for local relocations
and could shift global references incorrectly.

I reproduced the failure against that unmodified upstream revision using
`test_mixed_c_and_repeated_local_section_relocations` in
[tools/so3/tests/test_scaffold.py](../tools/so3/tests/test_scaffold.py). The fixture
combines two assembly functions with local references and a C function, without
a `.rodata` section. Upstream accesses `rodata_section_indices[0]` and raises
`IndexError: list index out of range` because that list is empty.

With the patch applied, the same fixture passes and its linked bytes match the
direct compiler/assembler reference. The upstream comparison used an isolated
copy, with the wrapper pointed at it and the `temp_dir` argument omitted because
upstream doesn't have that API extension. This confirms the relocation failure
separately from the temporary-file change. The full boot and 15 overlay byte
comparisons also passed after the patch was integrated.

The `temp_dir` extension is for keeping temporary sources out of `src/`. The
wrapper sends them to `build/`. The original
source directory stays on the include path so local `.h` and `.hpp` files still
resolve. The synthetic tests compare mixed C/ASM and C++/ASM output against a
direct compiler/assembler link. They include repeated local references, calls
across C, C++, and assembly, a constructor, and overloaded methods. Changing the
source must change the output, and a failed compile must preserve the previous
valid object.

Splat's default input subalignment is four bytes. Field's text and the Lib text
tail starting at file offset `0xE6B20` override it to 16 bytes: all mapped function
starts in those regions are 16-byte aligned. Earlier Lib code includes functions
on eight-byte boundaries, so the override does not cover the entire module.

CodeWarrior emits a separate `.text` section for each function. Assembly
placeholders contain their original trailing padding, while compiled functions
rely on the linker to honor alignment. The first 12-byte source replacement
exposed this: four-byte subalignment placed the next function four bytes early.
The region-specific settings restore the original gap. Check complete binaries
as well as individual function bytes when replacing a placeholder.

The build tracks source files, referenced assembly, tools, configuration, and
compiler files. This MWCC doesn't support `-gccdep`, so changes to any `.h`,
`.hpp`, or `.inc` header under `include/` or `src/` rebuild all C/C++ units. Splat
runs at most two jobs at once; compilation uses up to eight, capped by the CPU
count. Enter through `make build` or the Python build commands so newly added
sources and headers are included in the graph.

Large regions are grouped at detected function starts into roughly 64 KiB units.
Those divisions make compilation practical while original translation-unit
boundaries are still unknown. Functions that introduce data will also need
additional section mapping before they can replace their placeholders.

## Checks so far

All 26 tool tests pass in the pinned container after compiler setup. The complete
boot and 15 overlay rebuilds also pass `make verify`, and an unchanged build
reports no work to do.

The zeroing-loop example above was checked in the full boot build. Changing its
loop bound from 16 to 15 failed verification. Removing generated assembly caused
Splat to recreate it while keeping the edited source. An isolated Field
initializer split also created `.cpp`, preserved a source edit, and regenerated
missing assembly exactly. The 54 C++ renames kept all placeholder contents.

These checks establish the compile-and-compare workflow. Original C++ ABI
settings, runtime behavior, and the remaining data and VU boundaries still need
their own evidence.
